## 개선 전 실행 계획

댓글 조회는 `post_no` 인덱스가 없어 5건을 반환하기 위해 25,000행을 읽었다.

```text
Index scan on community_comments using PRIMARY
actual rows=25000
Filter: community_comments.post_no = 8192
result rows=5
actual time=0.024..16.9ms
```

모집글 첫 페이지는 기본키 역순으로 1,020행을 읽어 20건을 반환했고, 페이지 개수 계산은 게시글 5,000행을 전체 스캔했다.

```text
RECRUIT list: actual rows scanned=1020, result rows=20, actual time=0.897..0.918ms
RECRUIT count: table scan actual rows=5000, result rows=4000, actual time=1.85ms
```

## 적용 개선

- 댓글 조회: `(post_no, no)` 복합 인덱스
- 카테고리별 최신 게시글 및 개수 조회: `(category, no)` 복합 인덱스

## 인덱스 적용 직후 실행 계획

이 단계의 결과는 SQL 실행계획 개선만 입증한다. API p95와 RPS 개선 여부는 동일한 k6 조건의 3회 재측정을 완료한 후 판단한다.

댓글 조회는 인덱스로 필요한 5행만 읽으며 SQL 실행시간이 약 `16.9ms`에서 `0.06ms`로 감소했다.

```text
Index lookup using idx_community_comments_post_no_no
actual rows=5
actual time=0.0157..0.0595ms
```

모집글 첫 페이지는 카테고리 복합 인덱스로 필요한 20행만 읽었고, 페이지 개수 계산은 테이블 스캔 대신 커버링 인덱스를 사용했다.

```text
RECRUIT list: index lookup actual rows=20, actual time=0.015..0.051ms
RECRUIT count: covering index lookup actual rows=4000, actual time=0.973ms
```

다음 단계는 동일한 데이터, k6 프로필, Dev 서버 조건으로 3회 재측정해 RPS, 전체 p95, 엔드포인트별 p95, 실패율과 MySQL CPU를 비교하는 것이다.
